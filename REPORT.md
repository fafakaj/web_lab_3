## 2. Слои приложения

```
HTTP-запрос
   │
   ▼
security/   AuthenticationFilter  — кто это? (проверка JWT)
            AuthorizationFilter   — что ему можно? (@RolesAllowed)
   │
   ▼
resource/   StudentResource, AuthResource   — контроллеры: разобрать запрос, проверить формат, вызвать сервис
   │                 ▲ dto/ (StudentRequest, StudentResponse, ...)
   ▼
service/    StudentService, AuthService     — бизнес-логика: правила дат, уникальность, токены
   │                 ▲ entity/ (Student, User, RefreshToken)
   ▼
repository/ StudentRepository, ...          — запросы к БД через EntityManager (JPA)
   │
   ▼
PostgreSQL
```

Каждый слой знает только про слой под собой:

- **Ресурс** не обращается к БД и не содержит правил. Он превращает HTTP в вызов метода сервиса.
- **Сервис** не знает про HTTP. Он получает DTO, работает с сущностями и бросает исключения
  (`ConflictException`, `ResourceNotFoundException`). В ответ HTTP их превращают мапперы.
- **Репозиторий** знает только про БД: найти, сохранить, удалить.

Так было и в лабораторной работе №2 (`routes.py`, `service.py`, `repository.py`), только теперь
слои — это классы Java, а связывает их контейнер CDI через `@Inject`.

**DTO и сущность — разные классы.** `Student` (сущность) описывает строку таблицы: в нём
столбец `group_name`, геттеры и сеттеры для JPA. `StudentResponse` (DTO) описывает JSON
для клиента: поле `group`, имена в `snake_case`. Благодаря этому можно менять таблицу и не ломать API.
У пользователя разница ещё важнее: в `User` есть хеш пароля, а в `UserResponse` его нет, поэтому
хеш никогда не уйдёт клиенту. Перекладывает данные `StudentMapper`.

## 3. Путь запроса

Пример: администратор меняет комнату студента.

```
PATCH /api/requests/412345
Authorization: Bearer eyJhbGciOi...
Content-Type: application/json

{"room": "1401"}
```

1. **Open Liberty** принимает соединение и передаёт запрос в Jakarta REST. Префикс `/api`
   задан в `StudentsApplication` (`@ApplicationPath("/api")`).
2. **`RequestLogFilter`** запоминает время начала (фильтр `@PreMatching` работает до выбора метода).
3. **Выбор метода.** Jakarta REST ищет класс с `@Path("/requests")` и метод с `@PATCH` и
   `@Path("/{isu_id}")`. Это `StudentResource.patch()`. Не нашёл — 404 или 405.
4. **`AuthenticationFilter`** читает заголовок `Authorization`, проверяет подпись и срок JWT
   (`JwtService.verify()`) и кладёт в запрос логин и роль (`JwtSecurityContext`). Токен
   поддельный или истёк — 401.
5. **`AuthorizationFilter`** через рефлексию читает аннотацию `@RolesAllowed("ADMIN")` на
   методе `patch()`. Роль USER — 403.
6. **Чтение тела.** JSON-P превращает тело в `JsonObject`. Битый JSON — 400.
7. **`StudentResource.patch()`** проверяет формат ИСУ, берёт текущего студента у сервиса,
   накладывает изменения (JSON Merge Patch) и проверяет результат аннотациями (`RequestValidator`).
   Ошибка формата — 422.
8. **`StudentService.replace()`** с аннотацией `@Transactional`: контейнер открывает транзакцию.
   Сервис проверяет правила дат и копирует поля в сущность `Student`.
9. **EclipseLink** при завершении транзакции видит, что поле `room` изменилось, и сам выполняет
   `UPDATE students SET room = '1401' WHERE isu_id = '412345'`. Транзакция фиксируется (commit).
10. **Ответ.** Метод возвращает `StudentResponse`, JSON-B превращает его в JSON, статус 200.
11. **`RequestLogFilter`** пишет в лог: `PATCH /api/requests/412345 -> 200 (15 мс, пользователь: admin)`.

Если на любом шаге брошено исключение, Jakarta REST ищет для него **`ExceptionMapper`**
(пакет `exception`) и отдаёт ответ с ошибкой в едином формате.

## 4. База данных

Схема — в `src/main/resources/META-INF/sql/schema.sql`. EclipseLink выполняет этот скрипт при каждом
старте (настройка в `persistence.xml`). `CREATE TABLE IF NOT EXISTS` не трогает уже созданные таблицы.
В конце скрипта 25 команд `INSERT` добавляют студентов для примера. `ON CONFLICT (isu_id) DO NOTHING`
пропускает студента, если ИСУ уже есть, поэтому повторный старт не создаёт дублей.

```
students                     users                          refresh_tokens
─────────────────────        ─────────────────────────      ────────────────────────────
isu_id     PK                id            PK               id          PK
full_name                    username      UNIQUE           jti         UNIQUE
group_name                   email         UNIQUE           user_id     FK -> users.id
dormitory                    password_hash                  expires_at
room                         role  CHECK (ADMIN/USER)       revoked
check_in                     created_at
check_out  (NULL = живёт)
is_foreign
notes
```

- **students** — студенты. Первичный ключ — ИСУ: он уникален по заданию и не меняется.
- **users** — пользователи. Уникальность логина и почты проверяет сервис (ответ 409 с понятным
  сообщением), а ограничение `UNIQUE` в БД — последняя защита.
- **refresh_tokens** — выданные refresh-токены. Внешний ключ `user_id` связывает токен с
  пользователем: **один пользователь — много токенов** (вход с нескольких устройств).
  В Java это поле `@ManyToOne User user` в `RefreshToken`.

**Транзакции.** Методы сервисов, которые меняют данные, помечены `@Transactional`. Контейнер
начинает транзакцию до метода и фиксирует её после. Если метод бросил исключение, транзакция
откатывается, и в БД не остаётся половины изменений.

## 5. Вход и токены

```
Клиент                                         Сервер
  │ POST /api/auth/login {username, password}    │
  │ ───────────────────────────────────────────► │ BCrypt сверяет пароль с хешем из users
  │ ◄─────────────────────────────────────────── │ access (15 мин) + refresh (7 дней)
  │                                              │ jti refresh-токена записан в refresh_tokens
  │ GET /api/requests                            │
  │ Authorization: Bearer <access>               │
  │ ───────────────────────────────────────────► │ проверка подписи и срока
  │ ◄─────────────────────────────────────────── │ 200
  │            ... прошло 15 минут ...           │
  │ GET /api/requests  (старый access)           │
  │ ───────────────────────────────────────────► │
  │ ◄─────────────────────────────────────────── │ 401 TOKEN_EXPIRED
  │ POST /api/auth/refresh {refresh_token}       │
  │ ───────────────────────────────────────────► │ подпись, срок, jti есть в БД и не отозван
  │                                              │ старый refresh отозван (revoked = true)
  │ ◄─────────────────────────────────────────── │ новые access + refresh
  │ GET /api/requests  (новый access)            │
  │ ───────────────────────────────────────────► │ 200
```

Фронтенд делает обмен сам: функция `request()` в `js/api.js` получает 401, вызывает
`refreshTokens()` и повторяет запрос. Пользователь ничего не замечает.

**Почему refresh-токены хранятся в БД.** JWT нельзя «отозвать»: сервер проверяет только подпись
и срок. Для access-токена это допустимо — он живёт 15 минут. Refresh-токен живёт 7 дней, поэтому
сервер записывает его номер (`jti`) в таблицу. Так работают:

- **выход** — `POST /api/auth/logout` ставит `revoked = true`;
- **ротация** — каждый refresh-токен работает один раз;
- **защита от кражи** — если пришёл уже использованный refresh-токен, значит, его копия есть
  у кого-то ещё. Сервер отзывает все токены пользователя (`AuthService.refresh()`).

## 6. Проверка данных и ошибки

Проверка идёт в три ступени — как в лабораторной работе №2:

| Ступень | Что проверяет | Где | Код ответа |
|---|---|---|---|
| Чтение JSON | тело — JSON-объект, типы полей (`"is_foreign": "yes"` — ошибка), нет лишних полей | JSON-B, настройки в `JsonConfig` | 400 или 422 |
| Формат полей | обязательные поля, шаблоны (группа `M3301`, комната `1205`), длина | аннотации в DTO, `RequestValidator` | 422 |
| Бизнес-правила | даты заселения и выселения, уникальность ИСУ, логина и почты | `StudentService`, `AuthService` | 422, 409 |

По умолчанию JSON-B «мягкий»: число `412345` в строковом поле молча становится строкой `"412345"`,
а строка `"yes"` в логическом поле — значением `false`. Поэтому в `JsonConfig` подключены строгие
правила чтения: строки только из JSON-строк, `true`/`false` только из JSON-значений `true`/`false`,
неизвестное поле — ошибка.

**Централизованная обработка ошибок.** Сервисы бросают исключения — наследники `ApiException`.
Каждое знает свой статус и код:

```
RuntimeException
└── ApiException                (status, code, details)
    ├── InvalidRequestException     400 BAD_REQUEST
    ├── UnauthorizedException       401 UNAUTHORIZED / INVALID_TOKEN / TOKEN_EXPIRED
    ├── AccessDeniedException       403 FORBIDDEN
    ├── ResourceNotFoundException   404 NOT_FOUND
    ├── ConflictException           409 CONFLICT
    └── DataValidationException     422 VALIDATION_ERROR
```

Один класс `ApiExceptionMapper` превращает любой из них в ответ единого формата. Ещё три маппера
ловят ошибки, которые бросает не наш код: `JsonbExceptionMapper` (плохой JSON),
`WebApplicationExceptionMapper` (404 на неизвестный адрес, 405, 415) и `UnexpectedExceptionMapper`
(всё остальное → 500, трассировка в лог).

## 7. Ответы на вопросы к защите

### 1. Java в серверной веб-разработке. Особенности языка и платформы JVM

**Java** — язык со строгой статической типизацией: тип каждой переменной известен при компиляции,
поэтому многие ошибки видны до запуска. Компилятор `javac` переводит код не в машинные команды,
а в **байткод** (`.class`). Байткод выполняет **JVM** (Java Virtual Machine) — виртуальная машина,
которая есть для Windows, Linux и macOS. Отсюда принцип «написал один раз — запускаешь везде».

Особенности JVM, важные для сервера:

- **JIT-компиляция.** JVM следит, какой код выполняется часто, и переводит его в машинные команды.
  Поэтому сервер на Java после «прогрева» работает быстро.
- **Сборщик мусора.** Память под объекты освобождается автоматически, `free` писать не нужно.
- **Настоящие потоки.** В отличие от Python, в Java нет GIL: потоки работают параллельно на разных
  ядрах. Сервер обрабатывает каждый запрос в своём потоке из пула. Отсюда же ответственность:
  общие данные надо защищать (в проекте бины не хранят изменяемого состояния между запросами).
- **Экосистема.** Стандарты (Jakarta EE), серверы приложений, библиотеки (EclipseLink, java-jwt), сборщик Maven.

**Сравнение с лабораторной работой №2:** в Python тип проверялся во время работы (Pydantic),
здесь многое ловит компилятор; вместо `uvicorn` — сервер приложений Open Liberty.

### 2. Spring Boot и Java EE / Jakarta EE: основные отличия и подходы к разработке

**Jakarta EE** (раньше Java EE) — набор **стандартов** (спецификаций): Jakarta REST, CDI, JPA,
Bean Validation и другие. Стандарт описывает аннотации и интерфейсы, а реализацию даёт
**сервер приложений** (Open Liberty, WildFly, GlassFish, Payara). Приложение собирается в **WAR**
и разворачивается на сервере. База данных, транзакции и безопасность настраиваются в сервере
(у нас — `server.xml`), приложение берёт их по имени (`jdbc/studentsDS`).

**Spring Boot** — **фреймворк** одной компании. Приложение собирается в «толстый» JAR, внутри
которого уже есть встроенный Tomcat, и запускается командой `java -jar`. Настройки — в
`application.yml`. Spring даёт больше свободы (можно залезть в контейнер руками через
BeanPostProcessor), Jakarta EE даёт стандарт и гарантии: код на аннотациях стандарта
переносится между серверами.

| | Jakarta EE (наш проект) | Spring Boot |
|---|---|---|
| Что это | стандарт + сервер приложений | фреймворк |
| Сборка | WAR на сервере | fat JAR со встроенным Tomcat |
| Контроллер | `@Path`, `@GET`, `@PathParam` | `@RestController`, `@GetMapping`, `@PathVariable` |
| Внедрение | `@Inject`, `@ApplicationScoped` (CDI) | `@Autowired`, `@Service` |
| Ошибки | `ExceptionMapper` | `@ExceptionHandler` |
| БД | JPA (у нас EclipseLink) | Spring Data JPA (обычно Hibernate) |
| Безопасность | `@RolesAllowed`, Jakarta Security / свои фильтры | Spring Security |

### 3. ООП в Java: классы, интерфейсы, наследование и полиморфизм

- **Класс** — описание объектов: поля и методы. Пример: `Student` — поля `isuId`, `fullName`,
  методы `getRoom()`, `setRoom()`. **Инкапсуляция:** поля `private`, доступ — через методы.
- **Интерфейс** — набор методов без реализации, «договор». Пример: `ExceptionMapper<T>` из
  Jakarta REST требует метод `toResponse()`. Наши `ApiExceptionMapper`, `JsonbExceptionMapper`
  и другие его **реализуют** (`implements`). Так же `JwtSecurityContext implements SecurityContext`
  и фильтры `implements ContainerRequestFilter`.
- **Наследование** — класс получает поля и методы родителя (`extends`). Пример: `ApiException` —
  абстрактный родитель с полями `status`, `code`, `details`; `ConflictException`,
  `ResourceNotFoundException` и другие — наследники, которые только задают свой статус.
- **Полиморфизм** — один код работает с объектами разных классов через общий тип.
  `ApiExceptionMapper` принимает `ApiException` и вызывает `e.getStatus()`: для
  `ConflictException` это 409, для `ResourceNotFoundException` — 404. Маппер не знает,
  какой именно наследник пришёл, и ему это не нужно.

Ещё два вида классов в проекте: **record** (`StudentRequest`, `StudentResponse`) — короткая запись
неизменяемого класса-данных, Java сама создаёт конструктор, геттеры, `equals`; **enum** (`Role`) —
тип с фиксированным набором значений `ADMIN`, `USER`.

### 4. Аннотации в Java и их использование в серверных приложениях

**Аннотация** — метка в коде: `@Path("/requests")`, `@NotNull`, `@Transactional`. Сама по себе
аннотация **ничего не делает**. Её читает другой код — фреймворк — через **рефлексию** (возможность
программы во время работы узнать, какие у класса методы, поля и аннотации).

Этим аннотация отличается от декоратора Python из лабораторной работы №2: декоратор — функция,
он сам оборачивает другую функцию. Аннотация — пассивная метка.

Чтобы аннотацию было видно во время работы, у неё должно быть `@Retention(RUNTIME)`.
В проекте есть **своя аннотация** — `@QUERY` (`resource/QUERY.java`):

```java
@Target(ElementType.METHOD)        // вешается на метод
@Retention(RetentionPolicy.RUNTIME) // видна во время работы
@HttpMethod("QUERY")               // для Jakarta REST это HTTP-метод QUERY
public @interface QUERY {}
```

И есть **свой код, который читает аннотации**: `AuthorizationFilter` через рефлексию берёт
`@RolesAllowed` с метода и решает, пускать ли пользователя:

```java
RolesAllowed rolesAllowed = method.getAnnotation(RolesAllowed.class);
```

Кто читает остальные аннотации проекта:

| Аннотация | Кто читает | Что делает |
|---|---|---|
| `@Path`, `@GET`, `@POST`, `@PathParam` | Jakarta REST | маршрутизация |
| `@Inject`, `@ApplicationScoped` | CDI | создаёт объекты и связывает их |
| `@Entity`, `@Table`, `@Column`, `@Id` | JPA (EclipseLink) | связь класса с таблицей |
| `@NotNull`, `@Pattern`, `@Size` | Bean Validation | проверка полей DTO |
| `@Transactional` | CDI-перехватчик | открывает и закрывает транзакцию |
| `@JsonbProperty` | JSON-B | имя поля в JSON |
| `@ConfigProperty` | MicroProfile Config | значение из окружения |
| `@Operation`, `@Tag` | MicroProfile OpenAPI | описание для Swagger |
| `@RolesAllowed`, `@PermitAll` | наш `AuthorizationFilter` | права доступа |

### 5. Dependency Injection и Inversion of Control

**Inversion of Control (IoC, инверсия управления)** — не наш код создаёт объекты и управляет их
жизнью, а **контейнер**. Мы только описываем, что нужно.

**Dependency Injection (DI, внедрение зависимостей)** — способ IoC: объект не создаёт свои
зависимости через `new`, контейнер сам передаёт их.

Без DI:

```java
public class StudentService {
    private StudentRepository repository = new StudentRepository(); // сервис сам решает, какой репозиторий
}
```

С DI (так в проекте, контейнер — CDI):

```java
@ApplicationScoped                    // это бин: контейнер создаст один объект на приложение
public class StudentService {
    @Inject
    StudentRepository repository;     // контейнер сам подставит готовый репозиторий
}
```

Что это даёт:

- классы не связаны жёстко: в тесте можно подставить другой репозиторий;
- контейнер может подменить объект **прокси** и добавить поведение. Пример — `@Transactional`:
  на самом деле в `StudentResource` внедряется не `StudentService`, а его подкласс-обёртка,
  которая открывает транзакцию, вызывает настоящий метод и фиксирует транзакцию;
- зависимости проверяются при запуске: если для `@Inject` нет подходящего бина, приложение
  не развернётся.

**Скоупы** (сколько живёт объект): `@ApplicationScoped` — один на всё приложение (сервисы,
репозитории); `@RequestScoped` — новый на каждый запрос; ресурсы Jakarta REST по умолчанию
создаются на каждый запрос. Поэтому в бинах `@ApplicationScoped` нет полей, которые меняются
от запроса к запросу: их видят все потоки сразу.

`@PersistenceContext EntityManager em` в репозиториях — тоже внедрение: сервер даёт
`EntityManager`, привязанный к текущей транзакции.

### 6. Архитектура backend-приложения. Разделение ответственности между слоями

См. [раздел 2](#2-слои-приложения). Коротко:

| Слой | Пакет | Отвечает за | Не делает |
|---|---|---|---|
| Контроллер | `resource` | HTTP: путь, метод, параметры, статус ответа | не ходит в БД, не содержит правил |
| Сервис | `service` | бизнес-правила, транзакции | не знает про HTTP и JSON |
| Репозиторий | `repository` | запросы к БД | не содержит правил |
| Модель | `entity` | строки таблиц | — |
| DTO | `dto` | формат JSON API | — |

Зачем делить: каждый класс меняется по одной причине (сменили БД — правим репозиторий; сменили
правило дат — сервис). Код проще читать и проверять. Это **Separation of Concerns** из лекции 4.
**Coupling** (связанность) между слоями низкий: слой знает только интерфейс соседа снизу.
**Cohesion** (связность) внутри класса высокая: в `StudentService` только логика студентов.

### 7. Исключения в Java и централизованная обработка ошибок

**Исключение** — объект, который «выбрасывается» (`throw`) при ошибке и прерывает выполнение,
пока его не поймают (`try/catch`). Все исключения — наследники `Throwable`:

- **checked** (`Exception`, например `IOException`) — компилятор требует обработать или объявить их в `throws`;
- **unchecked** (`RuntimeException`) — обрабатывать не обязательно. Наши исключения — unchecked:
  сервис бросает их, а ловит не каждый метод, а один обработчик наверху.

**Централизованная обработка** — ошибки ловятся в одном месте, а не в каждом методе.
В Jakarta REST это `ExceptionMapper<T>`: класс с аннотацией `@Provider`, который превращает
исключение типа `T` в HTTP-ответ. Для каждого исключения выбирается маппер самого близкого типа:
`ConflictException` → `ApiExceptionMapper` (маппер для родителя `ApiException`), а любое
непредвиденное → `UnexpectedExceptionMapper` (маппер для `Throwable`).

Плюсы: единый формат ошибок, сервис не знает про HTTP-статусы напрямую, трассировка 500-й ошибки
пишется в лог, но не уходит клиенту (это защита: по трассировке можно узнать устройство сервера).
Иерархия исключений проекта — в [разделе 6](#6-проверка-данных-и-ошибки).

`@Transactional` откатывает транзакцию, если метод бросил unchecked-исключение. В
`AuthService.refresh()` это поведение изменено: `dontRollbackOn = UnauthorizedException.class` —
при повторном использовании токена отзыв всех токенов должен сохраниться в БД, хотя метод
и закончился ошибкой.

### 8. Реляционные базы данных. Таблицы, строки, столбцы, первичные и внешние ключи

**Реляционная БД** хранит данные в **таблицах**. **Столбец** — одно свойство с типом
(`room VARCHAR(4)`), **строка** — одна запись (один студент). Запросы пишут на SQL.

- **Первичный ключ (PRIMARY KEY)** — столбец, который однозначно определяет строку: уникален и не
  `NULL`. У `students` — `isu_id`, у `users` — `id` (число, выдаёт сама БД: `BIGSERIAL`).
- **Внешний ключ (FOREIGN KEY)** — столбец, который ссылается на первичный ключ другой таблицы.
  `refresh_tokens.user_id REFERENCES users (id)`: БД не даст записать токен несуществующего
  пользователя. `ON DELETE CASCADE` — при удалении пользователя удаляются и его токены.
- **Ограничения:** `NOT NULL` (поле обязательно), `UNIQUE` (логин и почта не повторяются),
  `CHECK (role IN ('ADMIN', 'USER'))` (роль только из списка).

Почему БД, а не JSON-файл, как в лабораторной работе №2: БД сама следит за целостностью
(ключи, ограничения), даёт транзакции, быстро ищет и сортирует, работает с несколькими
процессами сервера одновременно. Схема проекта — в [разделе 4](#4-база-данных).

### 9. Связи между сущностями: один-к-одному, один-ко-многим, многие-ко-многим

| Связь | Пример | Как хранится в БД |
|---|---|---|
| **один-к-одному** | пользователь — его профиль | внешний ключ с `UNIQUE` в одной из таблиц |
| **один-ко-многим** | пользователь — его refresh-токены (**есть в проекте**) | внешний ключ на стороне «многих»: `refresh_tokens.user_id` |
| **многие-ко-многим** | студенты — кружки (студент ходит в несколько кружков, в кружке много студентов) | отдельная таблица-связка с двумя внешними ключами: `student_clubs(student_id, club_id)` |

В JPA связи описываются аннотациями: `@OneToOne`, `@OneToMany` / `@ManyToOne`, `@ManyToMany`.
В проекте связь со стороны токена:

```java
@ManyToOne(optional = false)            // много токенов -> один пользователь
@JoinColumn(name = "user_id")           // столбец внешнего ключа
private User user;
```

Обратную сторону (`@OneToMany List<RefreshToken> tokens` в `User`) мы не объявляли: список токенов
пользователя в коде не нужен, а лишняя связь — лишние запросы.

### 10. ORM: назначение, преимущества и особенности отображения объектов на реляционную модель

**ORM (Object-Relational Mapping)** — библиотека, которая связывает объекты Java со строками таблиц.
Стандарт ORM в Java — **JPA** (Jakarta Persistence). По варианту реализация — **EclipseLink**
(в Open Liberty она встроена).

Класс помечается аннотациями, и ORM сама пишет SQL:

```java
@Entity @Table(name = "students")
public class Student {
    @Id @Column(name = "isu_id") private String isuId;
    @Column(name = "group_name") private String group;   // поле group -> столбец group_name
}
```

| Код | SQL, который выполнит EclipseLink |
|---|---|
| `em.find(Student.class, "412345")` | `SELECT ... FROM students WHERE isu_id = ?` |
| `em.persist(student)` | `INSERT INTO students ...` |
| `student.setRoom("1401")` внутри транзакции | `UPDATE students SET room = ? ...` при commit |
| `em.remove(student)` | `DELETE FROM students WHERE isu_id = ?` |

Запросы со списком пишутся на **JPQL** — это SQL, но по классам и полям Java:
`SELECT s FROM Student s WHERE s.group = :group ORDER BY s.fullName`.
Значения передаются **параметрами** (`:group`), а не вклеиваются в строку — это защита от SQL-инъекции.
Поле сортировки приходит от клиента, поэтому в `ORDER BY` попадает только значение из белого
списка `SORT_FIELDS` в `StudentRepository`.

**Преимущества ORM:** меньше ручного SQL; работа с объектами, а не со строками результата;
не надо вручную писать `UPDATE` — ORM отслеживает изменения «управляемых» сущностей.

**Особенности и подводные камни** («объектно-реляционный разрыв»):

- в Java есть наследование и ссылки на объекты, в БД — таблицы и внешние ключи; ORM переводит одно в другое;
- имена не совпадают (`group` — зарезервированное слово SQL, поэтому столбец `group_name`);
- ленивая загрузка связей и проблема «N+1 запросов»: при обходе списка ORM может сделать отдельный
  запрос на каждую связанную запись;
- чтобы понять, какой SQL выполняется, иногда нужно смотреть лог ORM.

### 11. Транзакции в базе данных. Основные свойства транзакций и их применение

**Транзакция** — группа операций с БД, которая выполняется целиком или не выполняется вовсе.
Свойства **ACID**:

- **Atomicity (атомарность)** — всё или ничего. При ошибке изменения откатываются (rollback).
- **Consistency (согласованность)** — после транзакции все ограничения БД (ключи, `UNIQUE`, `CHECK`) соблюдены.
- **Isolation (изолированность)** — параллельные транзакции не видят незафиксированных изменений друг друга.
- **Durability (долговечность)** — после фиксации (commit) данные сохранятся даже при сбое сервера.

**В проекте** транзакциями управляет сервер (JTA, `transaction-type="JTA"` в `persistence.xml`).
Метод с `@Transactional` выполняется в транзакции:

```java
// упрощённо, полный код — в AuthService
@Transactional(dontRollbackOn = UnauthorizedException.class)
public TokenResponse refresh(String token) {
    RefreshToken stored = findRefreshToken(token);
    stored.setRevoked(true);          // 1) старый токен отозван
    return issueTokens(stored.getUser()); // 2) новый токен записан
}
```

Шаги 1 и 2 — одна транзакция. Если шаг 2 упадёт, отзыв из шага 1 откатится, и пользователь
не останется без токена.

Почему `@Transactional` стоит на сервисе, а не на репозитории: одна бизнес-операция часто
делает несколько запросов (проверить, что ИСУ свободен, и вставить), и они должны быть в одной
транзакции.

### 12. Аутентификация и авторизация. Различия между ними

- **Аутентификация** — «**кто** это?». Проверка личности: логин и пароль при входе, подпись JWT
  на каждом запросе. Неудача — **401 Unauthorized**.
- **Авторизация** — «**что** ему можно?». Проверка прав по роли. Неудача — **403 Forbidden**.

Авторизация невозможна без аутентификации: сначала узнаём, кто пришёл, потом — что ему можно.

В проекте это два разных фильтра с приоритетами `Priorities.AUTHENTICATION` и `Priorities.AUTHORIZATION`
(аутентификация выполняется раньше):

| | `AuthenticationFilter` | `AuthorizationFilter` |
|---|---|---|
| Вопрос | кто это? | можно ли ему этот метод? |
| Читает | заголовок `Authorization: Bearer ...` | аннотации `@RolesAllowed`, `@PermitAll` на методе |
| Результат | логин и роль в `SecurityContext` | пропустить или 401 / 403 |

Пример: USER с верным токеном вызывает `DELETE /api/requests/412345`. Аутентификация пройдена
(токен верный), авторизация — нет (нужна роль ADMIN) → 403.

### 13. JWT: устройство токена, подпись, access- и refresh-токены

**JWT (JSON Web Token)** — строка из трёх частей через точку: `header.payload.signature`.
Каждая часть закодирована в base64url.

```
eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9   .   eyJzdWIiOiJhZG1pbiIsInJvbGUiOiJBRE1JTiIs...   .   3fK9...
            header                                        payload                                  signature
{"alg":"HS256","typ":"JWT"}                  {"iss":"web_lab_3", "sub":"admin",
                                              "role":"ADMIN", "type":"ACCESS",
                                              "iat":1759900000, "exp":1759900900}
```

- **header** — алгоритм подписи;
- **payload** — данные (claims): `sub` — логин, `role` — роль, `type` — вид токена, `iat` — когда выдан, `exp` — когда истекает;
- **signature** — подпись `HMAC-SHA256(header + "." + payload, JWT_SECRET)`.

**Токен не зашифрован**: payload может прочитать кто угодно (вставьте токен на jwt.io).
Поэтому в нём нет пароля и секретов. **Подпись** гарантирует, что токен не подделан: изменить
роль на `ADMIN` нельзя — подпись перестанет сходиться, а новую без `JWT_SECRET` не посчитать.

**HS256** — один общий секрет для подписи и проверки (у нас один сервер, это подходит).
**RS256** — подпись закрытым ключом, проверка открытым: удобно, если токены проверяют другие сервисы.

**Stateless:** сервер не хранит сессии, на каждом запросе он только проверяет подпись и `exp`.
Минус — выданный токен нельзя отозвать до истечения. Поэтому токенов два:

| | access-токен | refresh-токен |
|---|---|---|
| Зачем | доступ к API | получить новый access-токен |
| Куда отправляется | в каждом запросе, заголовок `Authorization` | только на `/api/auth/refresh` |
| Срок | 15 минут | 7 дней |
| Хранится на сервере | нет | номер `jti` в таблице `refresh_tokens` |
| Можно отозвать | нет (живёт недолго) | да (`revoked = true`) |

Поле `type` в токене не даёт использовать refresh-токен вместо access и наоборот.
Как идёт обмен токенов — в [разделе 5](#5-вход-и-токены).

### 14. Ролевая модель доступа и защита серверных ресурсов

**Ролевая модель (RBAC, Role-Based Access Control)** — права выдаются не каждому пользователю,
а **роли**; у пользователя есть роль. В проекте две роли (`enum Role`):

| Операция | USER | ADMIN |
|---|---|---|
| список, поиск, один студент (GET, QUERY) | да | да |
| создание, изменение, удаление (POST, PUT, PATCH, DELETE) | нет, 403 | да |

Права описаны **аннотациями прямо на методах** `StudentResource`:

```java
@RolesAllowed({"USER", "ADMIN"})        // на классе: читать могут обе роли
public class StudentResource {
    @DELETE @Path("/{isu_id}")
    @RolesAllowed("ADMIN")              // на методе: удалять — только ADMIN
    public Response delete(...) { ... }
}
```

Проверяет их `AuthorizationFilter` — **на сервере**. Фронтенд прячет кнопки «Редактировать» и
«Удалить» от USER, но это только удобство: запрос вручную (Postman, curl) всё равно получит 403.
**Права нельзя проверять только на клиенте** — клиент полностью под контролем пользователя.

Другие меры защиты в проекте:

- регистрация всегда даёт роль USER (поле `role` в теле — ошибка 422); первый ADMIN создаётся из `.env`;
- роль берётся из подписанного токена — подменить её нельзя;
- при неверном входе ответ одинаковый для неверного логина и неверного пароля: нельзя узнать, какие логины есть;
- в `ORDER BY` попадают только поля из белого списка, значения в запросах — параметрами (защита от SQL-инъекций);
- ответ 500 не содержит трассировки.

### 15. Хеширование паролей. Назначение соли и применение алгоритмов типа BCrypt

**Хеш** — результат односторонней функции: из пароля легко получить хеш, из хеша пароль — нельзя.
В БД хранится только хеш. При входе сервер хеширует введённый пароль и сравнивает хеши.
Если базу украдут, паролей в ней не будет.

**Соль** — случайная строка, которая добавляется к паролю перед хешированием. Зачем:

- без соли одинаковые пароли дают одинаковые хеши — сразу видно, у кого пароль `123456`;
- без соли работают **радужные таблицы** — заранее посчитанные хеши популярных паролей.

С солью у двух пользователей с паролем `qwerty123` хеши разные, и заранее посчитанные таблицы бесполезны.

**Почему BCrypt, а не SHA-256.** SHA-256 создан быть быстрым: видеокарта перебирает миллиарды
вариантов в секунду. **BCrypt специально медленный**, и его медленность настраивается
параметром **cost** (у нас 12, то есть 2¹² раундов: в зависимости от компьютера от 0,2 до 1 секунды на один хеш).
Для одного входа это незаметно, для перебора — очень долго. Когда компьютеры станут быстрее,
cost можно увеличить.

BCrypt сам создаёт соль и хранит её внутри хеша:

```
$2a$12$R9h/cIPz0gi.URNNX3kh2OPST9/PgBkqquzi.Ss7KIUgO2t0jWMUW
 │   │  └ соль (22 символа)   └ хеш (31 символ)
 │   └ cost = 12
 └ версия алгоритма
```

В коде (`PasswordHasher`):

```java
BCrypt.hashpw(password, BCrypt.gensalt(12)); // при регистрации
BCrypt.checkpw(password, hash);              // при входе: соль берётся из самого хеша
```

Особенность: BCrypt учитывает только первые 72 байта пароля. Поэтому `AuthService` отклоняет
более длинные пароли, а не обрезает их молча.

### 16. Хранение конфигурации, секретов и параметров окружения в backend-приложении

**Конфигурация** — всё, что меняется между окружениями (компьютер разработчика, тестовый сервер,
продакшен): адрес БД, пароли, секрет JWT, порт. Её **не пишут в код**:

- секрет в коде попадёт в git, и его увидят все, у кого есть доступ к репозиторию;
- чтобы поменять пароль БД, не нужно пересобирать приложение;
- один и тот же собранный WAR работает в любом окружении.

**Как устроено в проекте** (принцип 12-factor app: настройки — в переменных окружения):

```
.env  ──►  liberty-maven-plugin копирует в server.env  ──►  переменные окружения сервера
                                                          │
                ┌─────────────────────────────────────────┤
                ▼                                         ▼
     server.xml: ${DB_HOST}, ${HTTP_PORT}       Java: @ConfigProperty(name = "JWT_SECRET")
     (подключение к БД, порт)                   (JwtService, StartupData)
```

- **`.env`** — настоящие значения. Он в `.gitignore` и **не попадает в репозиторий**.
- **`.env.example`** — пример со всеми параметрами и пояснениями. Он в репозитории: по нему
  видно, что нужно для запуска.
- **`server.xml`** задаёт значения по умолчанию (`<variable name="DB_HOST" defaultValue="localhost"/>`);
  переменная окружения с тем же именем их заменяет.
- **`@ConfigProperty`** (MicroProfile Config) внедряет значение в поле Java-класса. Если обязательной
  переменной нет, приложение не запустится и напишет, какой именно.
- Неверная настройка обнаруживается **при старте**, а не при первом запросе: короткий `JWT_SECRET`
  или плохой пароль администратора останавливают запуск с понятным сообщением.

В настоящем продакшене секреты хранят ещё надёжнее: в хранилищах секретов (HashiCorp Vault,
Kubernetes Secrets, менеджеры секретов облаков), а не в файле на диске.
